OFFICIAL SOURCE ANALYSIS

模块化系统提示 — 110+ 片段的工业级 Prompt 工程

Claude Code 的系统提示不是一个巨型字符串，而是 110+ 个独立模块按会话状态动态组装。本文深入分析这套模块化架构的分类体系、缓存策略、A/B 测试机制和组装流程。

为什么不是一个大 prompt

传统的 AI 应用通常将系统提示写成一个很长的字符串，随着功能增加不断追加内容，最终变成一个难以维护的庞然大物。Claude Code 采用了完全不同的策略：模块化系统提示架构。

整个系统提示被拆分为 110+ 个独立模块，每个模块负责一个明确的职责域。主系统参数包含约 22 个独立模块，涵盖身份定义、行为规则、工具使用指南、安全约束等核心维度。每个模块都是一个可独立启用或禁用的单元，可以针对不同用户群体进行 A/B 测试。

社区研究者 Piebald-AI 的 GitHub 仓库对 Claude Code 的提示进行了系统性逆向工程，记录了 255 个文件，分为 6 大类。这些文件的总量揭示了现代 AI Agent 在 prompt 工程上的投入远超外界想象。

模块化的核心优势

  • 独立部署：修改某个模块不影响其他模块，降低回归风险
  • A/B 测试：每个模块都可以作为独立实验单元
  • 缓存友好：静态模块可以全局缓存，动态模块按会话缓存
  • 团队协作：不同团队可以独立维护各自负责的模块
  • 按需组装：根据用户的当前模式、功能权限、MCP 工具等条件，动态选择需要加载的模块

模块分类体系

根据 Piebald-AI 的逆向分析，Claude Code 的系统提示模块被组织为 6 大类。每一类服务于不同的功能层面，从 Agent 行为控制到 SDK 参考数据，覆盖了一个完整 AI Agent 所需的全部指令集。

分类 数量 职责描述 代表性模块
Agent Prompts ~35 个 控制 Agent 在不同模式下的行为逻辑，包括规划、探索、记忆整合、安全监控和子任务执行 dream-memory-consolidation, explore, plan-mode-enhanced, security-monitor, worker-fork-execution, coordinator-dispatch
Data/Reference ~27 个 为模型提供各语言 SDK 用法、API 参考和工具使用模式的结构化知识 python-sdk-patterns, typescript-sdk-patterns, API references (Python, TypeScript, Java, Go, Ruby, PHP, Rust, Elixir), tool-use-reference, model-catalog
Skill Prompts ~15 个 定义特定技能的执行流程和约束，例如用 Claude API 构建应用、调试、简化代码等 build-with-claude-api, computer-use-mcp, debugging, simplify, verify-skill, codebase-to-course
System Prompts Core ~90+ 个 系统提示的核心骨架，涵盖模式切换、工具用法说明、任务执行规范、记忆管理和行为洞察 模式定义 (normal/plan/coordinator/proactive)、工具描述模板、任务执行约束、CLAUDE.md 注入逻辑、auto-memory 索引规则
System Reminders ~40+ 个 在对话过程中动态注入的提醒片段，用于保持模型对当前状态的感知 Plan mode 提醒, hooks 状态, file states 更新, team coordination 信号, session management 指令, MCP 工具变更通知
Tool Descriptions ~70+ 个 每个可用工具的 JSON Schema 描述和使用指南 Bash, Read, Write, Edit, Grep, Glob, TaskCreate, TaskUpdate, WebFetch, WebSearch, ComputerUse

规模感知

如果将所有模块的内容拼接在一起，总文本量超过 10 万 tokens。当然，任何单次会话都不会加载全部模块——系统会根据当前上下文精准选择需要的子集。这种"按需加载"的策略既保证了指令的完整性，又避免了不必要的 token 浪费。

双层缓存策略

模块化架构带来的一个关键优化机会是 prompt 缓存。Anthropic API 支持 prompt caching（提示缓存），允许将频繁重复的 prompt 前缀缓存到服务器端，避免每次请求都重新处理相同的文本。Claude Code 利用这一特性设计了精巧的双层缓存策略。

缓存分割标记

系统提示中存在一个隐藏标记 __SYSTEM_PROMPT_DYNAMIC_BOUNDARY__，它将整个 prompt 分为两段，分别适用不同的缓存策略：

============================================================ SYSTEM PROMPT 缓存架构 ============================================================ +----------------------------------------------------------+ | | | [全局缓存层] TTL = 1 小时，所有用户共享 | | | | - 身份定义 (You are Claude, made by Anthropic...) | | - 行为规则 (NEVER do X, always do Y...) | | - 工具使用指南 (Bash, Read, Write, Edit...) | | - 安全约束 (permission model, deny rules...) | | - 模式说明 (normal, plan, coordinator, proactive) | | | +----------------------------------------------------------+ | | | __SYSTEM_PROMPT_DYNAMIC_BOUNDARY__ | | | +----------------------------------------------------------+ | | | [会话缓存层] TTL = 5 分钟，per-session 缓存 | | | | - CLAUDE.md 内容 (项目级 + 用户级) | | - git status 快照 | | - MCP 工具列表与指令 | | - auto-memory 索引 | | - 当前 skill 描述 | | - system-reminder 动态注入 | | | +----------------------------------------------------------+

全局缓存层：标记之前

标记之前的内容是身份、行为规则、工具指令等对所有用户都完全相同的静态文本。这部分内容在 Anthropic 的服务器端以 1 小时 TTL 缓存，所有用户共享同一份缓存。这意味着当你向 Claude Code 发送请求时，系统提示的前半段不需要重新处理，直接命中缓存。

会话缓存层：标记之后

标记之后的内容是 per-session 的动态数据——你的 CLAUDE.md 文件内容、当前仓库的 git status、已连接的 MCP 工具列表等。这些数据在 5 分钟 TTL 内缓存，但仅对当前会话有效。每个用户的每个会话都有自己独立的动态缓存。

危险区域标记

代码中存在一个特殊的标签 DANGEROUS_uncachedSystemPromptSection，它明确告诉工程师："这里的内容会破坏缓存前缀"。任何被此标签包裹的内容都不会被缓存，每次请求都需要重新处理。这是一个工程纪律工具——它提醒开发者，将高变化率的内容放在缓存边界之前会导致缓存失效，从而增加延迟和成本。

缓存命中的成本影响

Anthropic API 的 prompt caching 价格模型中，缓存命中的 token 成本大约是非缓存 token 的 1/10。对于 Claude Code 这样系统提示极长的应用来说，缓存策略直接影响运营成本。假设全局缓存层有 5,000 tokens，每次请求如果命中缓存可以节省约 90% 的 prompt 处理费用。按照 Claude Code 的日活用户量，这是一笔非常可观的节省。

A/B 测试机制

模块化架构的另一个关键优势是 可实验性。每个模块都是一个独立的可测试单元，Anthropic 团队可以针对任意模块进行对照实验，而不影响系统的其他部分。

GrowthBook Feature Flags

Claude Code 使用 GrowthBook 作为 feature flag 管理平台。每个 prompt 模块都可以关联一个或多个 feature flag，通过 flag 的开关状态决定模块是否加载。具体机制如下：

  • 模块启用/禁用：通过 flag 控制某个模块是否出现在最终的系统提示中
  • 多变体实验：同一个模块可以有多个变体版本（A/B/C），不同用户组看到不同的版本
  • 灰度发布：新模块可以先向 5% 的用户开放，观察效果后再逐步扩大
  • 紧急回滚：如果某个模块导致问题，可以在几分钟内通过 flag 关闭，无需发布新版本

对用户的影响

这就是为什么不同用户可能会观察到 Claude Code 的行为存在细微差异。你和同事使用同一版本的 Claude Code，但你们看到的系统提示可能包含不同的模块组合。例如：

  • 某些用户可能收到更积极的代码审查建议，而其他用户收到更保守的建议
  • 某些用户的 Claude Code 可能倾向于使用 Edit 工具，而其他用户的更倾向于使用 Write
  • 安全约束的措辞可能在不同用户组之间有所不同，以测试哪种表述更有效

这种实验驱动的迭代方式使得 Anthropic 团队能够用数据指导 prompt 优化，而不是凭直觉或猜测。

"NEVER" 比 "always" 更强

社区研究者在分析 Claude Code 的系统提示时发现了一个显著的模式：否定约束（"NEVER do X"）的使用频率远高于正面约束（"always do Y"）。这不是偶然的——每一条 "NEVER" 规则背后都对应着一个曾经被观察到的具体失败模式。

换言之，Claude Code 的系统提示是从真实故障中"打补丁"迭代出来的产物，而不是一次性设计的理想规范。每当模型在生产环境中展现出某种不期望的行为，工程师就会添加一条针对性的 "NEVER" 约束来修正它。这种方法论类似于安全工程中的"事故后回顾 + 修复"循环。

代表性的 "NEVER" 规则示例

Git 安全类：

  • NEVER update the git config — 防止模型修改用户的 Git 配置
  • NEVER run destructive git commands (push --force, reset --hard, checkout ., restore ., clean -f, branch -D) unless the user explicitly requests — 防止不可逆的代码丢失
  • NEVER skip hooks (--no-verify, --no-gpg-sign, etc) unless the user explicitly requests it — 确保 Git hooks 不被绕过
  • NEVER run force push to main/master, warn the user if they request it — 对主分支的特殊保护

文件操作类：

  • NEVER create documentation files (*.md) or README files unless explicitly requested — 防止模型主动创建不必要的文档
  • NEVER commit files that likely contain secrets (.env, credentials.json, etc) — 防止敏感信息泄露
  • NEVER write new files unless explicitly required — 优先编辑现有文件而非创建新文件

行为控制类：

  • NEVER use the TodoWrite or Agent tools（在特定上下文中） — 防止在不当场景使用某些工具
  • NEVER mention a skill without actually calling this tool — 防止模型"空谈"而不执行
  • NEVER push to the remote repository unless the user explicitly asks — 防止未经授权的远程推送

这些规则的共同特点是：它们都非常具体，针对的是某个确切的失败场景，而不是抽象的原则。这说明每条规则都来自真实的生产事故或用户投诉。

为什么否定约束更有效

从 LLM 对齐的角度看，否定约束比正面约束更有效有几个原因：

  • 边界明确："永远不要做 X" 定义了一个清晰的禁区，而 "总是做 Y" 在边界条件下可能产生歧义
  • 失败模式可枚举：具体的失败模式是有限的、可列举的，而理想行为是无限的、难以穷举的
  • 注意力权重：研究表明 LLM 对否定词（NEVER, DO NOT）的注意力权重更高，在约束遵从上效果更好
  • 可验证性：违反 "NEVER" 约束很容易被自动检测，而 "always" 约束的遵从难以量化评估

Token 预算管理

每个 prompt 模块都有自己的 token 开销。在上下文窗口有限的情况下（即使是 200K token 的窗口），系统提示占用的空间直接影响留给用户对话的可用空间。因此，模块的 token 成本是一个需要精确管理的资源。

模块规模分布

不同模块的 token 规模差异巨大：

模块类型 Token 数量 说明
最小模块（简短提醒） ~12 tokens 例如一条简短的行为提醒或状态标记
中等模块（工具描述） ~200-800 tokens 单个工具的 JSON Schema 和使用说明
安全监控提示 ~3,169 tokens 包含完整的安全策略、权限检查规则和危险命令列表
最大模块（完整 SDK 参考） ~5,106 tokens 完整的 Python tool-use 参考，包含示例代码和模式说明

预算分配策略

所有被加载的模块的 token 总和构成了系统提示的总长度。以一次典型的会话为例，加载的模块可能包括：核心身份（~500 tokens）+ 行为规则（~2,000 tokens）+ 当前模式说明（~300 tokens）+ 已启用工具描述（~3,000 tokens）+ CLAUDE.md（~500 tokens）+ 动态提醒（~200 tokens），总计约 6,500 tokens。

在 200K token 的上下文窗口中，这仍然只是一个很小的比例。但对于需要处理大型代码库的长对话来说，每一个 token 都很宝贵。这也是为什么系统采用"按需加载"策略——如果用户没有使用某个 SDK，就不加载对应的 SDK 参考模块。

组装流程

当用户启动一个新的 Claude Code 会话或发送一条消息时，系统会执行以下完整的 prompt 组装流程。每一步都是确定性的——给定相同的输入条件，组装出的 prompt 完全一致。

============================================================ SYSTEM PROMPT 组装流程（9 步） ============================================================ Step 1: 加载核心身份模块 │ "You are Claude, made by Anthropic..." │ 基础行为规则、响应格式、安全基线 │ v Step 2: 根据当前模式选择对应模块 │ ┌─ normal mode → 标准工具使用 + 对话指南 │ ├─ plan mode → 规划约束 + 只读工具集 │ ├─ coordinator → Worker 调度 + 任务分配 │ └─ proactive → 心跳机制 + Brief 生成 │ v Step 3: 注入工具描述 │ - 根据 feature flags 过滤可用工具 │ - 根据 deny rules 移除被禁止的工具 │ - 为每个工具生成 JSON Schema + 使用指南 │ v Step 4: 注入 CLAUDE.md + Rules │ - 项目级 .claude/CLAUDE.md │ - 用户级 ~/.claude/CLAUDE.md │ - .claude/rules/*.md 规则文件 │ v Step 5: 注入 auto-memory 索引 │ - 从 ~/.claude/memory/ 加载记忆条目 │ - 按相关性排序和筛选 │ v Step 6: 注入 MCP 工具名称 │ - 已连接的 MCP 服务器列表 │ - 每个 MCP 工具的描述和参数 │ - MCP 服务器提供的 instructions │ v Step 7: 注入 Skill 描述 │ - 当前可用的 skill 名称和触发条件 │ - skill 的简要说明 │ v Step 8: 拼接为最终 prompt │ 将以上所有片段按固定顺序拼接 │ v Step 9: 插入缓存分割标记 在静态/动态边界处插入 __SYSTEM_PROMPT_DYNAMIC_BOUNDARY__ 完成最终 prompt 构建
模式选择的具体规则

Step 2 中的模式选择取决于多个条件：

  • Normal mode：默认模式，用户直接与 Claude 对话，所有工具可用
  • Plan mode：用户通过 /plan 命令或 Shift+Tab 切换进入，模型只能进行分析和规划，不能执行修改操作
  • Coordinator mode：KAIROS 功能激活时，主 Agent 进入协调者角色，负责将任务分配给 Worker
  • Proactive mode：KAIROS 功能的一部分，Agent 可以在用户不主动提问时自发执行任务

每种模式不仅加载不同的指令模块，还会改变可用工具的集合。例如，Plan mode 下 Write 和 Edit 工具被移除，确保模型无法修改文件。

工具过滤的详细逻辑

Step 3 中的工具注入不是简单地列出所有工具，而是经过多层过滤：

  1. Feature flag 过滤：通过 GrowthBook flag 控制哪些工具可用（例如 TaskCreate 只在特定实验组启用）
  2. Deny rules 过滤：用户在 settings.json 中可以禁止某些工具，被禁止的工具不会出现在 prompt 中
  3. 模式过滤：不同模式下可用工具不同（Plan mode 移除写操作工具）
  4. MCP 工具合并：来自 MCP 服务器的工具与内置工具合并，形成最终的可用工具列表
  5. Deferred tools：部分不常用的工具以 "deferred" 形式存在，只展示名称，需要模型主动请求才加载完整 schema

对 Prompt 工程的启示

Claude Code 的模块化系统提示架构不仅是一个产品实现，更是一套可供所有 AI Agent 构建者参考的 Prompt 工程方法论。以下是从中提炼出的关键模式：

模式一：模块化拆分

不要写一个巨型 prompt。将系统提示拆分为职责明确的独立模块，每个模块负责一个功能域。这样做的好处是：修改某个行为只需要改对应的模块，不会意外影响其他行为；新功能以新模块的形式添加，而不是在现有 prompt 末尾追加。

模式二：缓存感知设计

将系统提示分为"静态层"和"动态层"。静态层（身份、规则、工具说明）可以利用 prompt caching 大幅降低延迟和成本。动态层（用户配置、会话状态）按需注入。两层之间用明确的标记分隔，确保缓存前缀的稳定性。

模式三：迭代式约束

从失败中学习，用 "NEVER" 打补丁。不要试图一次性设计出完美的 prompt——这是不可能的。相反，建立一个快速反馈循环：部署 → 观察失败 → 添加约束 → 重新部署。每条 "NEVER" 规则都应该有对应的失败案例作为支撑。

模式四：可测试性

每个模块独立可测。通过 feature flags 控制模块的启用/禁用，通过 A/B 测试量化每个模块的效果。这要求模块之间保持低耦合——模块 A 的启用不应依赖于模块 B 的存在。

对所有构建 Agent 的人的建议： 如果你正在构建基于 LLM 的 Agent 系统，Claude Code 的模块化 prompt 架构提供了一个经过大规模验证的参考方案。从小规模开始——先将你的 prompt 拆分为 3-5 个模块（身份、工具、规则、动态上下文），然后随着系统复杂度增长逐步细化。记住：prompt 工程不是一次性工作，而是一个持续迭代的过程。每当模型出现不期望的行为时，思考应该在哪个模块添加什么约束，而不是在 prompt 末尾随意追加文本。
