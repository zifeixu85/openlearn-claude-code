OFFICIAL SOURCE ANALYSIS

Agent 设计模式与未发布能力

从 Claude Code 源码中提炼的 10 个通用 Agent 设计模式，以及 ULTRAPLAN、完整 Feature Flags 列表与安全绕过漏洞分析。

从 Claude Code 提炼的通用 Agent 设计模式

Ken Huang 在分析 Claude Code 架构时提出了一个核心论点："生产级 AI 的挑战不在模型，而在 Harness。模型提供智能，Harness 提供控制。" 这意味着，一个生产级 AI Agent 的价值不仅在于底层语言模型的能力，更在于围绕模型构建的控制层——Harness——如何管理状态、约束行为、处理故障并优化资源。

以下 10 个设计模式并非 Claude Code 独有。它们是从 Claude Code 工程实践中提炼出来的通用架构方法，任何 Agent 系统都可以借鉴和复用。 它们覆盖了从基础架构到运维可观测的完整链路，为构建健壮的 Agent 系统提供了蓝图。

适用范围：这些模式同样适用于基于 OpenAI、Gemini 或开源模型构建的 Agent 系统。核心思想是将"智能"与"控制"分离——模型负责推理，Harness 负责工程质量。无论底层模型如何变化，Harness 层的设计模式保持稳定。

模式 1: Harness 范式

三层架构

Harness 范式将整个 Agent 系统分为三个清晰的层次：

三层架构概览
层级职责Claude Code 对应
模型层（Model）提供语言理解和推理能力Claude API 调用
Harness 层状态管理、工具调度、权限控制、错误恢复QueryEngine + ToolManager
UI 层用户交互、输入输出展示Ink 终端界面 / Web Dashboard

五大核心挑战

Harness 层需要解决的五个关键问题：

  • 约束动作空间 —— 限制模型可以调用的工具和可以执行的操作范围，防止模型做出危险行为
  • 管理对话状态 —— 维护上下文窗口、处理消息历史、执行压缩和截断策略
  • 执行安全 —— 通过权限系统和沙箱机制保障操作安全
  • 处理故障 —— 网络超时、API 限速、工具崩溃等异常的优雅恢复
  • 优化资源 —— token 用量、API 调用次数、并发度的精细管理

在 Claude Code 中，这五个挑战分别对应了 ToolManager、MessageHistory、PermissionPipeline、ErrorRecovery 和 ResourceOptimizer 等子系统。

设计启示：大多数 Agent 开发者将 90% 的精力放在模型调优上，但 Claude Code 的工程实践表明，Harness 层的复杂度和代码量远超模型调用层。一个成熟的 Agent 系统，模型调用可能只占代码库的 5%，其余全是 Harness 逻辑。

模式 2: 工具契约 (Tool Contract)

统一工具接口

每个工具必须实现相同的契约接口，包括五个维度：

  • 身份（Identity）—— 工具名称、描述、参数 schema
  • 执行（Execute）—— 工具的核心逻辑
  • 验证（Validate）—— 入参的类型安全校验
  • 权限（Permission）—— 该工具需要哪些权限等级
  • 展示（Render）—— 工具结果如何在 UI 中呈现

Zod Schema 类型安全

Claude Code 使用 Zod schema 对每个工具的输入参数进行类型安全验证。这确保模型生成的工具调用参数在到达执行逻辑之前已经经过了严格的类型检查，避免了运行时类型错误。

行为属性

工具还声明了两个关键的行为属性，用于调度优化：

  • isConcurrencySafe —— 标记工具是否可以安全地并发执行（如 Read、Grep 是并发安全的）
  • isReadOnly —— 标记工具是否为只读操作（只读工具可以跳过部分权限检查）

buildTool 工厂函数

buildTool 是工具注册的工厂函数。它采用保守默认值策略——所有工具默认不可并发、非只读、需要完整权限检查。开发者必须显式声明工具的安全属性才能获得优化待遇。这是安全第一的设计理念。

这种"默认安全"的设计选择意味着新增一个工具时，如果开发者忘记设置行为属性，工具会以最保守的方式运行（串行、需要完整权限），而不是以最宽松的方式运行。只有经过安全审查后，开发者才会显式标记工具为并发安全或只读。

模式 3: 查询引擎 (Query Engine)

中央编排器

查询引擎是 Agent 循环的核心。它管理 user-model-tool 三方交互：接收用户输入，发送给模型，解析模型输出中的工具调用，执行工具，将结果反馈给模型，如此循环直到任务完成。

Continue Sites 模式

这是查询引擎最精妙的设计之一。与简单的 try/catch 不同，Continue Sites 提供了多个精确的错误恢复出口，每个出口针对特定的故障场景：

四类 Continue Sites
恢复点触发条件恢复策略
上下文坍塌排空上下文窗口被填满压缩历史消息，释放空间后继续
反应式压缩接近 token 上限执行智能压缩，保留关键信息
最大输出 token 升级模型输出被截断提升 max_tokens 参数后重试
多轮继续任务未完成但模型停止注入"请继续"提示词，延续任务

这不是简单的异常捕获——每个 Continue Site 都有独立的状态检测、恢复逻辑和重入点。它们共同构成了一个精密的故障恢复网络。

关键区别：传统的 try/catch 是被动的——异常发生后才处理。Continue Sites 是主动的——在循环的每个关键节点设置检查点，检测是否需要恢复。这种设计让 Agent 能够在长时间运行的复杂任务中保持稳定，而不是在第一个异常时就崩溃。

模式 4: 分层权限 (Layered Permissions)

权限 Pipeline

每一次工具调用都要通过四层权限检查：

  • 通用规则 —— 全局黑白名单、基础安全策略
  • 工具特定检查 —— 每个工具可以定义自己的权限需求
  • 自动分类器 —— 使用 AI 对模糊请求进行风险评估
  • 用户审批 —— 最终的人类确认环节

操作模式

Claude Code 提供五种操作模式，控制自动化程度：

五种操作模式
模式行为
default标准交互模式，危险操作需要确认
auto自动执行大多数操作，仅极危险操作需要确认
plan只规划不执行，所有写操作被阻止
acceptEdits自动接受文件编辑，但其他操作仍需确认
bubble子代理模式，权限请求冒泡到父代理

中央门控函数 canUseTool

canUseTool 是所有权限检查的汇聚点。它接收工具名称和参数，经过完整的 Pipeline 后返回三种状态：

  • allow —— 允许执行，无需用户确认
  • deny —— 拒绝执行，向用户说明原因
  • ask —— 需要用户确认后才能执行

这个函数是系统安全的最后防线。所有工具调用——无论来自主代理还是子代理——都必须通过这个门控点。

模式 5: 上下文管理 (Context Management)

三层压缩策略

当对话历史接近模型上下文窗口上限时，系统依次执行三层压缩：先移除冗余的工具输出，再对长消息进行摘要，最后整体压缩对话历史。每一层都尽可能保留关键信息，避免丢失任务上下文。

按需加载

上下文空间是稀缺资源。Claude Code 通过两种延迟加载策略节省空间：

  • Skills 两层加载 —— 先加载轻量的技能索引，仅在需要时加载完整技能定义
  • MCP 延迟发现 —— MCP 服务器的工具列表在首次使用时才获取

子代理上下文隔离

每个子代理拥有独立的上下文窗口。父代理通过结构化的消息传递与子代理通信，而不是共享上下文。这既避免了上下文污染，也防止了 token 浪费。

Transcript 持久化

完整的对话记录被持久化到磁盘，支持崩溃恢复和会话审计。Transcript 文件同时也是 Auto Memory 提取的数据源。

持久化策略采用增量写入——每条新消息在处理后立即追加到 transcript 文件中，而不是在会话结束时批量写入。这确保了即使进程意外终止，也只丢失最后一条未完成的消息，而非整个对话历史。

模式 6: 记忆架构 (Memory Architecture)

四层记忆

  • CLAUDE.md —— 用户手写的显式规则和偏好
  • Auto Memory —— 对话中自动提取的隐式知识
  • Session Memory —— 当前会话的短期记忆（上下文窗口内容）
  • Auto Dream —— 空闲时的记忆整合与巩固

索引与详情分离

MEMORY.md 只是一个索引文件，记录了每条记忆的摘要和引用路径。完整的记忆详情存储在独立的文件中。这种设计让系统可以快速扫描所有记忆的摘要，而只在需要时加载完整内容，显著节省上下文空间。

记忆整合（做梦机制）

Auto Dream 借鉴人类睡眠中的记忆巩固概念。在用户不活跃期间，系统对积累的记忆碎片进行去重、合并和关联建立，确保记忆库随时间推移越来越精炼，而非无限膨胀。这一功能通过 GrowthBook 的 tengu_onyx_plover flag 控制。

做梦机制的具体操作包括：识别语义重复的记忆条目并合并为一条、删除与当前项目状态矛盾的过时记忆、为相关但分散的记忆建立交叉引用。整个过程在后台静默执行，用户无需干预。

模式 7: 子代理编排 (Sub-Agent Orchestration)

两种子代理类型

  • 一次性 Subagent —— 为单个任务创建，任务完成后销毁，结果返回给父代理
  • 持久 Teammate —— 长期存活的 Worker，可以接收多个任务，拥有持久状态

上下文隔离 vs 共享通信

子代理拥有独立的上下文窗口（隔离），但通过结构化的消息通道与父代理通信（共享）。这种设计平衡了信息安全和协作效率——子代理不会被父代理的无关上下文干扰，同时又能获取完成任务所需的信息。

Coordinator 模式的四阶段工作流

Coordinator 模式是最复杂的编排策略，包含四个阶段：

  1. 规划阶段 —— 分析任务，将其分解为可并行的子任务
  2. 分配阶段 —— 将子任务分配给合适的 Worker
  3. 监控阶段 —— 追踪各 Worker 的进度，处理异常和超时
  4. 汇总阶段 —— 收集所有 Worker 的结果，解决冲突，合并为最终输出
编排 vs 直接调用：Coordinator 模式的核心价值在于——父代理不直接执行任务，而是专注于规划和协调。这让复杂任务可以被分解为可并行的子任务，每个 Worker 在独立的上下文中高效执行。这也是 KAIROS 系统实现大规模自主任务处理的基础。

模式 8: 错误恢复 (Error Recovery)

指数退避重试

对于 API 限速（429）和服务过载（529）错误，系统采用指数退避策略自动重试。每次重试的等待时间按指数增长，避免在服务恢复期间造成额外压力。

Circuit Breaker（熔断器）

当同一工具连续失败 3 次时，熔断器触发，暂停该工具的调用。这防止了失败的工具反复消耗 token 和时间。熔断状态会在一定时间后自动恢复尝试。

Persistent Retry（持久重试）

在无人值守模式（Headless）下，系统对 API 错误进行无限重试。因为没有用户在终端前等待，放弃重试意味着任务彻底失败。持久重试确保即使在临时性网络故障后，任务也能最终完成。

Crash Recovery（崩溃恢复）

每条消息在发送给模型前都会预写入磁盘（Write-Ahead Log）。如果进程意外崩溃，下次启动时可以从磁盘恢复对话状态，从中断点继续执行，而不是丢失整个会话。

错误恢复策略对比
策略触发条件恢复行为适用场景
指数退避429 / 529 错误递增等待后重试API 限速、服务过载
熔断器连续 3 次失败暂停工具调用持续性工具故障
持久重试Headless 模式下任何 API 错误无限重试无人值守任务

模式 9: 遥测与可观测 (Telemetry)

OpenTelemetry 集成

Claude Code 集成了 OpenTelemetry 标准，提供结构化的 trace 和 span 数据。每次 Agent 循环、工具调用、API 请求都被记录为独立的 span，支持端到端的性能分析和问题定位。

tengu_ 事件前缀

所有遥测事件使用统一的 tengu_ 前缀命名。这是 Claude Code 内部的代号体系，便于在大规模日志系统中快速过滤和聚合 Claude Code 相关的事件。

PII 处理

遥测数据在上报前经过严格的 PII（个人可识别信息）过滤。文件路径、用户名、代码片段等敏感信息被移除或哈希化，确保遥测合规性。

Feature Flag 驱动的 A/B 测试

通过 GrowthBook 平台的 Feature Flags，团队可以对不同的用户群体启用不同的功能变体，实现 A/B 测试。遥测数据与 Flag 状态关联，让团队能够量化每个功能变体的效果。

例如，tengu_ultraplan_model flag 可以控制 ULTRAPLAN 使用哪个底层模型，团队可以对比不同模型在规划任务上的表现。tengu_bramble_lintel 可以调节记忆提取的频率阈值，找到性能与质量的最优平衡点。

模式 10: 资源优化 (Resource Optimization)

并行 Prefetch（启动优化）

Claude Code 启动时并行执行多个预取操作：读取 CLAUDE.md、获取 Git 状态、检查 MCP 服务器、加载 Feature Flags。这种并行 prefetch 策略将启动时间从串行的数秒压缩到亚秒级。

工具并发调度

只读工具（如 Read、Grep、Glob）可以安全地并行执行，而写入工具（如 Edit、Write、Bash）必须串行执行以避免冲突。调度器根据工具的 isReadOnly 和 isConcurrencySafe 属性自动做出调度决策。

延迟加载

模块、工具定义和技能包都采用延迟加载——仅在首次需要时才加载到内存。这减少了启动时的内存占用和初始化时间。

Prompt Cache 分层

Claude API 支持 Prompt Cache，对于重复出现的系统提示词和工具定义，缓存命中后可以显著降低 token 费用和响应延迟。Claude Code 精心排列消息顺序以最大化缓存命中率——系统提示词和工具定义放在消息序列的最前面且保持稳定，这样它们会被缓存，而变化频繁的用户消息放在后面。

成本影响：Prompt Cache 命中时，缓存部分的 token 费用仅为正常价格的十分之一。对于 Claude Code 这样每次请求都携带大量系统提示词和工具定义的系统，这意味着每次 API 调用的实际成本可以降低 30-50%。

ULTRAPLAN: 30 分钟云端深度规划

实验功能提示：ULTRAPLAN 是一项未发布的实验性功能，目前仅通过 Feature Flag 对部分用户开放。以下信息基于源码分析，实际行为可能随版本更新而变化。

与 Plan Mode 的区别

普通 Plan Mode（plan 操作模式）是在本地 CLI 中运行的只读规划，不执行任何写操作。 ULTRAPLAN 完全不同——它在云端容器中启动一个独立的长时间思考进程，使用 Opus 4.6 模型（可通过 GrowthBook 的 tengu_ultraplan_model flag 配置），超时时间长达 30 分钟。

触发方式

ULTRAPLAN 通过关键词触发：在消息中包含 ultraplan 或 ultrareview 即可激活。系统内置了复杂的上下文检测逻辑以避免误触——例如在讨论 ULTRAPLAN 功能本身时不会触发。

阶段流转

ULTRAPLAN 的生命周期包含以下阶段：

ULTRAPLAN 生命周期
阶段位置行为
running云端容器执行深度分析，可能运行数十分钟
needs_input云端 → 用户遇到歧义或缺失信息，请求用户补充
approved用户 → 云端用户确认规划方案，授权执行
executing云端或本地执行已批准方案，或 teleport 到本地 CLI

用户可以通过浏览器实时监控 ULTRAPLAN 的执行进度。teleport 机制允许云端规划的结果被"传送"到本地 CLI，在用户的工作目录中直接执行，避免了云端容器访问本地文件系统的限制。

50 子命令安全绕过漏洞

安全警告：以下内容描述了一个已被修复的安全漏洞。了解这个漏洞有助于理解安全系统设计中的权衡取舍。

漏洞根源

文件：bashPermissions.ts，常量 MAX_SUBCOMMANDS_FOR_SECURITY_CHECK = 50。

当一条 shell 命令通过 &&、||、; 连接的子命令数量达到 50 个以上时，系统会跳过所有安全分析，直接放行该命令。这意味着任何被 deny rule 阻止的命令，只要前面拼接 50 个无害命令，就能绕过安全检查。

Adversa AI 的 PoC

安全研究机构 Adversa AI 构造了一个概念验证：50 个 true 命令通过 && 连接，后面追加一条 curl 命令。由于子命令数量超过阈值，整条命令绕过了 deny rule 检查，成功执行了网络请求。

内部原因

内部工单 CC-643 记录了设置这个阈值的原因：复杂的多子命令 shell 表达式在进行安全分析时会导致 UI 冻结。为了解决用户体验问题，工程师选择了在子命令数量过多时跳过安全分析。

修复方式

修复位于 bashPermissions.ts 第 2174 行：将超过阈值时的默认行为从 "ask" 改为 "deny"。即——当子命令过多无法完成安全分析时，默认拒绝而非默认放行。该修复已在 v2.1.90 中静默发布。

设计教训

这个漏洞揭示了安全系统设计中的一个经典陷阱：性能优化与安全保障之间的冲突。当复杂命令的安全分析导致 UI 冻结时，工程师选择了"跳过分析"而非"拒绝执行"。正确的做法应该是：当无法完成安全分析时，必须假设操作是危险的（fail-closed），而不是假设操作是安全的（fail-open）。

这也说明了为什么模式 4（分层权限）中 canUseTool 的默认返回值如此重要——默认行为决定了系统在异常场景下的安全姿态。

总结：从源码到方法论

这 10 个设计模式从不同维度覆盖了构建生产级 Agent 系统的核心工程挑战。Harness 范式确立了整体架构哲学；工具契约和查询引擎提供了执行基础；分层权限和上下文管理保障了安全与效率；记忆架构和子代理编排实现了复杂能力；错误恢复、遥测和资源优化则确保了系统在生产环境中的可靠运行。

ULTRAPLAN 和各种 Feature Flags 展示了 Claude Code 团队的功能迭代策略——通过严格的门控机制，新功能可以在小范围用户中验证后再逐步推广。而 50 子命令安全绕过漏洞的案例则提醒我们，即使是最优秀的工程团队，在性能与安全的权衡中也可能犯错。"默认拒绝"（fail-closed）应该是所有安全相关决策的铁律。
